## 3. How the two sides talk (the design, plan v6 §4)

- **On a Kissflow event** (a step entered or submitted): a Kissflow integration (I-1 … I-7).
- **On a screen action** (a new question round, an edited question, a reopen, the release request, a cancellation, a question-history update, a contact change): one webhook integration per action. The screen sends data only, and the target call is fixed in the integration.
- **The supplier's answers reach the app through `request.changed`:**
  1. the supplier's screen sends only the request id;
  2. the integration reads the request itself;
  3. it copies the 15 fields to the case named in the request's `App_Case_Item_Id`, which suppliers can't change.

  So a supplier can never write into another case.
- **Proven tonight:**
  - admin writes to fields that are read-only at the current step: S-5 (portal) and the app session's probe P-RO (app);
  - the release step, the go-to and the held step: the live walk;
  - the key's submit doesn't enforce mandatory fields (both sessions).
- **Still to test in the morning:**
  - the same REST calls made from an integration's HTTP connector;
  - whether a screen can call a webhook;
  - raw JSON in an HTTP body;
  - whether an app user can open a portal file.

## 3a. An independent code review of tonight's portal and shared code

Three reviewers read the code from different angles: data correctness, security, and fit with the prototype and plan. Each finding then went to a separate skeptic who tried to disprove it. That left **16 confirmed findings, which come down to 8 issues, and all 8 are fixed and tested**. 9 others were refuted.

| Issue | Fix |
|---|---|
| **After a reopen the supplier was stuck.** The go-to returned the request to "keep up to date", but the release lock and label stayed, so it could be neither edited nor released | The portal treats `Release_Flag` = "Reopened" as unlocked. The reopen integration (I-6) now also writes `Request_Locked` = No and the review label. The release request (I-5) clears the flag |
| **"Report a change" worked only once.** Nothing in v6 wrote the receipts | A report counts as sent after 10 minutes. New hand-off `change.received`: the app screen sends the receipts back |
| A file sent with a question answer was missing from the file list (`Documents_JSON`) and not synced | Written and synced now |
| The file-list write didn't check that the stored list matches the stored files | It does now, and re-applies otherwise |
| "Remove" marked only one of two duplicate rows | Every row of that file is marked |
| A file answering a question Beiersdorf hasn't closed could be removed | Refused, like B-15 for components |
| A contact without a portal user got the id `""` (merged into one person) | No id is written for such a contact |
| A failed sync to Beiersdorf was silent | The supplier sees "Saved, but Beiersdorf's copy was not updated yet" |
| A namesake could be taken for the contact | Matching is by id or e-mail; the name only for old contact rows that have neither |

**By design, not fixed:** "only a contact who may confirm can release" (B-11) is checked by the screen, because `Release_Contacts` holds every contact (decision 2 of 16 Oct, so everyone keeps seeing the case). To make Kissflow itself enforce it, `Release_Contacts` would hold only the confirmers, and the others would then lose sight of the case during the release.

## 4. Decisions for you

1. **A technical portal user, co-assigned on the supplier steps?** The walk showed that the step's assignee can move a supplier step through the API, with no mandatory check. If I-1 adds a technical portal user to `Assigned_Contacts` and `Release_Contacts`, the integrations can move the request into the final release and out of it on a reopen. The cost: Kissflow's task and deadline mails also go to that user. **The alternative:** the supplier's own screen moves the step when the case says so (plan §2).
2. **The question history in the portal:** it's one JSON field, replaced whole. Tonight the app screens send it only when they've read every open point of the case live (safe, but it may often wait). **Recommended:** keep each round's history on its own CIQP Query item, with a held step after "respond" so answered rounds stay visible, and per-item status writes. That's a portal change, not built tonight (plan §4.1 `history.updated`).
3. **App (from the app session):**

   - (b) the release request goes out when RMM next opens the app, not at the moment of the last completion: acceptable, or should the scheduler do it?
   - (c) the config editor stays read-only until a publish path is agreed.
4. **Reminders to all contacts:** the deadline reminders still go to the first contact only. If the builder lets you pick the whole field as recipient, change one step and the rest are copied.
