# CIQ final document service (Google Apps Script)

Kissflow-internal. Not for Beiersdorf.

The service makes the final PDF of every completed CIQ case once, with no RMM click (REQ-PROC-046, AS-12). A time trigger runs every 5 minutes. For each case that the final release I-7 has recorded and that has no final document yet, it does these steps:

1. Reads the case, its reviews, open points, audit rows, supplier and configuration over the Kissflow admin REST routes.
2. Builds the document with the app's own code. The content and the document seal are what the app's "Final document" tab shows when the tab names the same people. The tab is rebuilt for each viewer, and the viewer's own Kissflow name always wins there. So when a stored name differs from that person's Kissflow name, the tab shows another name and another seal. Nothing compares the two; the filed seal is the one in `Final_Document_Hash`. Example: the night runner's cases store a fictional BDF contact as the RMM owner's name.
3. Renders the PDF.
4. Attaches the PDF to `CIQ_Case_A00.Final_PDF`. Neither the custom screens nor Kissflow's own item view show that field: since 27 Oct the item view shows only the "navigate to the CIQ App" message, because its Details section is hidden. Check it in the app's data console (Admin or Developer role): CIQ Case, then the case's drawer.
5. Writes `Final_Document_Hash` and `Final_Document_At`, and `Completion_Trigger` when it is empty.
6. Mails the PDF to the RMM case owner.
7. Logs one "Final PDF" CIQ Audit Event row.

- When the case list carries `Final_Release_At`, an idle tick is 1 or 2 calls.
- When it does not, an idle tick reads up to `MAX_GETS_PER_TICK` cases at 1.2 s each, so about 30 s with the default 25.
- At 5 min that is 288 ticks a day, about 2.4 h: over the consumer quota.
- One filed case is about 40 calls, so 45–80 s plus Kissflow's answer times.

On a consumer account, set `TICK_MINUTES` to 15 and `MAX_GETS_PER_TICK` to 10 (about 96 ticks of 13 s, some 20 min a day). On Workspace the defaults fit.

## Reading the logs

Open Executions in the left sidebar and open a run. Every line starts with `[CIQ-FD] <step>` and is followed by JSON. The lines hold ids, case codes, counts, statuses and hashes only. They never hold a key, a token, a URL, an e-mail address or a person's name.

For one case, the lines come in this order:

1. `case start`
2. `read` (counts)
3. `built` (the seal and the counts)
4. `rendered` (the bytes and the SHA-256)
5. `attached`, or `attached PDF reused`
6. `case fields written`
7. `mail sent`, or `mail not sent` with the reason
8. `audit row written`
9. `case done`

Each tick ends with `tick done`, which gives the counts and the number of calls.

Problems show up as these lines:

- `case failed`: the attempt count and the error text. After 3 failed attempts, `ADMIN_EMAIL` gets one alert. The trigger then skips the case, and `runOnce` retries it.
- `case stopped: needs a person`: a retry cannot help, for example a file of the PDF's name on the case that is not this document. `ADMIN_EMAIL` gets the alert at once, and the trigger skips the case. Fix the cause, then run `runOnce`.
- `attach busy, tried again`: Kissflow answered 408, 409 or 423. The upload is tried again in the same run, up to 2 times.
- `attach refused`: see the next section.
- `case stopped: time is up`, `tick stopped: time is up`: the run neared Apps Script's 6-min limit. Nothing more is written, it is not a failed attempt, and the next tick resumes the case first.
- `case fields found written`: an earlier run's case-field `PUT` reached Kissflow but its answer was lost. The run only does the missing mail and audit row.
- `mail not confirmed`: a run stopped while it was sending the RMM mail. The mail is not sent twice; `ADMIN_EMAIL` is asked to check that it arrived.
- `pause 20 min`: the script got a 429 or a Cloudflare page. It makes no call until `PAUSE_UNTIL`. The shared-key rule then applies to both agent sessions too.
- `tick failed`, `probe failed`: an error outside a case, for example a missing Script Property.

The script keeps its own state in Script Properties:

- `PAUSE_UNTIL`
- `DONE_IDS` (cases filed or already filed)
- `ENDED_IDS` (cases that never get a document: rejected or withdrawn, or completed without a final release, or completed and cancelled; a completed item is locked). A cancelled case that is not completed is read again, so that a later reactivation would be seen; this version of the app cannot reactivate a case.
- `OLD_IDS`, `OLD_IDS_FOR` (completed cases released before `RELEASED_AFTER`; they are forgotten when `RELEASED_AFTER` changes)
- `RR_CURSOR`
- `FD_<caseItemId>`: one case's resumable state: attempts, last error, attachment id, hashes, the planned hash, the mail and audit-row steps

Deleting `FD_<id>` resets that case. Do not delete it after a `case fields found written`, `mail not confirmed` or failed-mail line: without it the script cannot tell its own filing from someone else's, and leaves the case alone. Deleting `PAUSE_UNTIL` ends a pause, but only do that when the 20 minutes are over.

## If Kissflow refuses the attachment

Attaching to a completed item works in dev (K-15, proven on 22 Oct: see "Proven live in dev"). I-7 completes the case about 17 s after the release, so the attach always goes to a completed item. This section is for the case that prod behaves differently.

When Kissflow refuses (a 4xx other than 408, 409, 423 or 429), the log shows `attach refused {"status":…}`, then `case failed`. No hash is written, no mail goes out and no audit row is logged. The case is retried on the next ticks. After 3 attempts, one alert goes to `ADMIN_EMAIL`.

A failure that is not a clear refusal (a 5xx, or a 2xx whose answer or read-back does not show the file) is retried the same way. With `DRIVE_FOLDER_ID` set, the third such failure counts as a refusal.

You can then choose one of these:

- **The Drive fallback.**
  1. Create a Drive folder and copy its id from the end of its URL.
  2. Set `DRIVE_FOLDER_ID`, and run `probe()`: it logs `probe: DRIVE_FOLDER_ID {"access":true}` when the script can open the folder.
  3. Run `runOnce` on the case.

  The PDF goes into the folder. Its description names the case item and the document seal; a file of the same name is reused only when both match, never another case's or cycle's file. The hash is written, and the audit row and the mail name the Drive file. `ADMIN_EMAIL` gets an alert. The file is shared view-only with the RMM only while `MAIL_ENABLED` is on, because sharing sends Google Drive's own mail; the alert says when it is not shared.
- **The two options from the spec.** Attach the PDF to `CIQ_Audit_Event_A00.Event_File`, or change I-7 to stop before "Skip and complete". Both need code or flow changes; they are your decision.

**A file of the PDF's name already on the case.** The script reuses it only when it carries this document's seal (in the PDF's Subject), as its own interrupted runs leave it. Any other file of that name, such as a probe upload or an older render, stops the case with `case stopped: needs a person` and an alert at once. Nothing is written, hashed or mailed. Remove the file from the case in Kissflow, then run `runOnce`.

The `PUT` of the case fields on a completed item works in dev too (22 Oct). If prod refuses it, the PDF stays attached and the log shows `case fields PUT failed: HTTP …`. The next run reuses the attached file and does not upload it twice.

## Mail on and off

- `MAIL_ENABLED` is `true` by default: **mail is on** unless you set it to `false`. With `false`:
  - no RMM mail goes out;
  - the audit row has no `Notify_Recipient` or `Notify_Channel`;
  - its history line leaves out "Sent to the RMM owner."
- The mail is template C-14:
  - subject `<Case_Code>: final document ready`;
  - the app's body text, plus one line saying the PDF is attached and filed on the case;
  - the PDF attached.
- **Recipient**, first match wins:
  1. an e-mail on `Owner_RMM`;
  2. `BDF_Contact_Email`, when the owner is the user who started the case (the app's rule);
  3. `FALLBACK_RMM_EMAIL`, with the owner's name in the body.

  Otherwise no mail goes out and `ADMIN_EMAIL` gets an alert.
- **Never twice.** The script records that it is about to send before it calls MailApp. If a run stops in between, the next run does not send again; it logs `mail not confirmed` and asks `ADMIN_EMAIL` to check.
- **Admin alerts** depend only on `ADMIN_EMAIL`; leave it empty for none.
- **MailApp's daily quota** is 100 mails on a consumer account and 1,500 on Workspace.
- **Not built:** the C-13 supplier receipt. It is not required by the requirements, and e-mails are out of scope in `PROD-READY-2026-10-21.md`.

## What it reads and writes

**Reads**, admin routes, with the key's headers:

- the `CIQ_Case_A00` list and items;
- the `CIQ_Review_A00` and `CIQ_Open_Point_A00` items of the case. They come from the `q` search plus every item the case's audit rows name. Each item is read in full and kept only when its `Case_Item_Id` is the case;
- the `CIQ_Audit_Event_A00` list, read once per run. A row without `Snapshot_JSON` is read in full;
- the case's `CIQ_Supplier_A00` row, read in full for its Contacts table;
- every `CIQ_Config_Version_A00` row in full, cached for 30 min.

It never reads the portal (`CIQP_*`), the RMES forms, internal notes, `CIQ_Case_Data_A00` or `CIQ_Scope_Run_A00`.

**Writes**, once per case:

1. **The attachment:** `POST …/CIQ_Case_A00/{id}/Final_PDF/attachment`, multipart part `file`, named `<Case_Code>-final-document.pdf`. It is skipped when a file of that name that carries this document's seal is already attached; a file of that name without it stops the case.
2. **The case fields:** `PUT …/CIQ_Case_A00/{id}` with:
   - `Final_Document_Hash` = `seal:<16-hex document seal> sha256:<SHA-256 of the PDF>`;
   - `Final_Document_At` (ISO, no milliseconds);
   - `Completion_Trigger` = "Final release by <name>", only when the field is empty.
3. **The audit row:** create, submit and read back a `CIQ_Audit_Event_A00` row:
   - `Event_Key` `<Case_Code>-FD-PDF`, category "Final PDF", action `final.pdf`, actor side System;
   - `New_Value_Text` with the file name, size, SHA-256, seal and attachment id;
   - `Notify_*` when the mail went out;
   - a `Snapshot_JSON` line the app's case history shows as "Generated final document".

Every write is read back and compared. Nothing else is written. It never submits a step and never writes to the portal.

## Safety rules

- **Never regenerated.** A case with `Final_Document_Hash` set is left alone, by every entry point.
- **Eligibility comes from Kissflow.** A case qualifies only when all of these hold:
  - `Final_Release_Confirm` is "Confirmed" and `Final_Release_At` is set;
  - it is not cancelled (a later reactivation would count; this version of the app cannot reactivate a case);
  - its status is not Rejected or Withdrawn;
  - it has settled: completed for at least `SETTLE_MINUTES`, or released at least 15 min ago;
  - for the trigger and `doPost`: released at or after `RELEASED_AFTER` (`runOnce` ignores it);
  - the app's own mapper sees it as completed.

  `doPost` takes only a case item id, and only with the right `DOPOST_TOKEN`.
- **The seal is checked.** It is verified with `verifyFinalDocument` before rendering.
- **One run at a time,** under the script lock (`probe` too).
- **The pacing rule.** At least 1.2 s between Kissflow calls. A 429 or an HTML answer pauses the script for 20 min.
- **The time limit.** No new case after 3 min, no case's first write with less than 2 min left, and no Kissflow call or mail after 5 min. Apps Script stops a run at 6 min. The next run resumes where it stopped.
- **Resumable without duplicates.** Each step is recorded before or right after it runs: the planned hash before the `PUT`, the mail before MailApp, the audit row's id right after its submit. A lost answer or a stopped run gives no second upload, mail or audit row.
- **Keys stay in Script Properties.** They are never logged and never in a mail. Every log line passes a redactor (keys, token, e-mail addresses, URLs).
- **The signed download** of an attached PDF is fetched with the key only when its host is `KF_DOMAIN`, and neither hop follows a redirect. It is used only to hash or mail a PDF that an earlier run attached, or to check the seal of a file of the PDF's name.
- **Production is yours.** You set up the prod project yourself; agents never touch prod. `test/live.mjs` runs only against account `AcDOSunMEpSA` on `dev-beiersdorf.kissflow.eu`.

## The PDF

- **Content:** the app's final document, from `toAppState` and `buildFinalDocument` on the same items, with the same seal. The offline test checks that it deep-equals the app's RMM-screen document for the fixture case ZZT-0005, including two closed open points: a returned round, a change by the raiser (AS-08), an attachment, and a point closed as not accepted.
- **Wording:** the tab's. `entry.ts` `displayCopy` prints the labels in place of the document's codes: market names, origin labels, the open-point kind, the action labels ("Returned to supplier", "Changed by the raiser", "Closed as not accepted") and the section tags ("Mandatory", "Optional", "Not applicable, justified"). The copy is made after the seal is checked; the seal is the document's.
- **Layout (27 Oct):** `sync/pdf.mjs` lays the PDF out as the app's Final document tab, so "Download PDF" and the filed PDF look like the screen. It is a small pure-JS PDF 1.4 writer with no dependency. It uses A4, Helvetica and Helvetica-Bold only (WinAnsi, nothing embedded), and the app's colour tokens converted to RGB (brand blue, ink, the greys, the soft fills). It draws:
  - **the header:** "CIQ FINAL DOCUMENT", the material and INCI, the case code, and the seal badge "Document seal: unchanged" (green) or "Document seal broken" (red), as the tab checks it;
  - **the case facts** in two columns, label above value, and the grey note "Created automatically at the supplier's final release …";
  - **the five parts** with the tab's headings:
    - part 1: label/value rows with who and when, and the metadata answers after the general section; the documents-only sections are a closing two-column "Further sections in scope" list;
    - parts 2 and 3: the K2.1 composition and the evidence as tables;
    - part 4: each open point as a bordered box with a grey strip and its rounds;
    - part 5: the confirmations, then the tab's grey closing band with the document id and the seal;
  - **on every page:** the footer `<Case_Code>-FD · document seal <seal>` with "Page X of Y"; from page 2 on, a running header with the case code and material.
- **Page breaks:** a heading always stays with what follows it. A row moves to the next page whole; only a row taller than a page is split, by lines. A table repeats its header row on the next page. An open-point box is closed at the page end and continues under a strip "… (continued)". The text is real, selectable text, and the output is deterministic: the same document always gives the same bytes.
- **Build-time patch.** `build.mjs` (and the app's `prototype/vite.finalpdf.ts`) applies the exact text patch in `src/pdf-patches.mjs` to `pdf.mjs` while bundling; the file on disk is unchanged. It swaps the seal wording of the retired sync service for the app's document seal:
  - the footer;
  - the closing note "The SHA-256 of this PDF is filed on the case (Final Document Hash).";
  - the PDF producer and subject. The subject is `document seal <seal>`, which the script reads back to recognise its own file.

  A patch that no longer matches stops the build. Dates come from `setDateFormat`: `TIME_ZONE`, for example "20 Oct 2026, 20:00 CEST".
- **Same bytes in the app and in Apps Script:** `prototype/src/features/rmm/finalPdf.test.ts` renders the same documents with the app's bundle and with `Bundle.gs` and compares the bytes: ZZT-0005, and a long document of more than 5 pages.
- **Samples:** `node kissflow-build/final-pdf/test/samples.mjs` writes these files to `out/samples/`, rendered with `Bundle.gs` and dated in Europe/Berlin:
  - `ZZT-0005-final-document.pdf`, the fixture case;
  - `ZZT-0099-final-document.pdf`, a fictional long case from `test/long-case.mjs`: 10 open points over up to 4 rounds, one answer taller than a page, 26 components, 26 documents, umlauts and accents;
  - on macOS, a PNG of every page (`…-page-<n>.png`).
- **What a PDF does not reproduce** compared with the tab:
  - **Fonts:** IBM Plex Sans and Mono become Helvetica. The codes (case code, CAS, versions) are not monospaced, justifications are not italic, and "medium" weight is bold.
  - **Icons:** the file and shield icons are simple drawn check marks. The paperclip is the word "Attachment:" in a thread and is left out in the evidence table.
  - **Interaction:** no tooltips, no Download button, no live re-check of the seal. The badge states the check made when the PDF was rendered; the service renders only a document whose seal verifies.
  - **Theme and width:** always the light theme on A4. The tab's phone layout and dark mode do not apply.
  - **Characters:** only WinAnsi (Western European). Others print as a close form (≤ as `<=`, → as `->`) or `?` (for example Ł, č, Greek, CJK).
  - **Kept although the tab leaves them out** (the PDF keeps every fact it held before): the applicability tag in the "Further sections in scope" list, and the time of "Case started". "(continued)" strips and repeated table headers are added at page breaks. Files are listed by name only and are never embedded.

## The live harness (dev only)

```
node kissflow-build/final-pdf/test/live.mjs <caseItemId>           # dry run: reads only
node kissflow-build/final-pdf/test/live.mjs <caseItemId> --apply   # the writes go to Kissflow
```

It runs `runOnce` from node, using the same two `.gs` files:

- It reads `KF_DOMAIN`, `KF_ACCOUNT_ID`, `KF_ACCESS_KEY_ID` and `KF_ACCESS_KEY_SECRET` from `Beiersdorf/.env` at run time and never prints them.
- It refuses to run unless `.env` names account `AcDOSunMEpSA` on `dev-beiersdorf.kissflow.eu`.
- curl gets the key through a temporary mode-600 header file (`-H @file`) in a mode-700 folder under the system temp folder, outside the project. It is deleted after each call. A run killed mid-call can leave one behind; the next start removes it. The key is never in curl's argv.
- It keeps 8 s between calls, and lifts the service's 5-min time limit (`RUN_LIMIT_S` 3600), which is for Apps Script only.
- It sets `MAIL_ENABLED=false`, so no mail is sent and none is recorded.
- It keeps the pause and resume state in `out/live-state.json`, without the connection. A dry run keeps only the pause there: its planned ids and hashes never reach an `--apply` run.

Without `--apply`, every write is answered locally and printed as a planned write, and the PDF goes to `out/<Case_Code>-final-document.pdf`. The offline test covers this harness with a curl stand-in.
