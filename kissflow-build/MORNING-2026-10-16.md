## 2. What I fixed in the portal screens

1. **Preview of uploaded files.** Every uploaded file now has a **Preview** button. It opens Kissflow's own file viewer through the SDK (`kf.client.openFilePreview`), with the file as Kissflow stored it. This works wherever files are listed: under a question, in a section's documents, in requested documents and next to an answer.
2. **Upload loader.**
   - While a file uploads, the upload box shows **"Uploading \<file name\>…"** with a spinner, and takes no second file.
   - The section header shows **"Uploading 1 file…"**.
   - Both disappear when the upload has finished. The "uploaded" message still comes only after Kissflow has stored the file.
3. **K2.1: a value disappearing while you type.**
   - **Cause:** after every save the page reloaded, and the components table then reset its rows from the reloaded data. So a value typed but not yet committed was wiped, like the CAS number right after the INCI name.
   - **Fix:** the table only follows the saved data when its content really changed elsewhere (a colleague's save, or a refused save), and never while you are typing in it.
   - **Test:** a new one types an INCI name and then a CAS number during a slow save. Both values stay and are saved.
4. **Slow saving.**
   - **Cause:** every autosave was followed by a full reload: all four task lists, then every item read in full.
   - **Fix:** an autosave now shows the request exactly as Kissflow read it back after the write. No reload. A full reload still happens after task actions, uploads and a failed save.
   - **What a save costs now:** 3 SDK calls (read → write → read back), all as the signed-in supplier, with no REST API calls. The first read must stay: Kissflow has no locking, and without it a save could overwrite a colleague's answers saved a moment earlier. The read-back must stay too, because it is how a lost write is noticed and redone.
5. **The final release on the new step.**
   - The screens find the release on the request's own step, write who released and when, and submit it.
   - At that step the questionnaire shows read-only, and any change is refused before anything is written.
   - A reopen (the go-to back to "keep up to date") makes the questionnaire editable again.
   - The old CIQP Final Release process is no longer read for new items.

## 4. Decisions for you (conflicts with the prototype)

1. **After the release the request ends, so the supplier loses it.** Kissflow lists only open tasks for a supplier. So after the release, the case disappears from the portal on the next visit, and "Report a change" can't be used. The prototype keeps showing "Your released questionnaire" with "Report a change". Tonight the screen keeps the released case visible until the page is closed; that's all the screen can do.
   - **My recommendation:** add one more step after the go-to step, "Supplier: view the released CIQ". It is never submitted, like "keep up to date", and only the change-report fields are editable. It's a 5-minute builder change, or I do it with your OK.
2. **Fill `Release_Contacts` with every case contact, not only those who may confirm.** Otherwise the other contacts lose sight of the case during the release. The screen already lets only a contact who may confirm give the release, which is the prototype's behaviour. The tests now use this setup.
3. **Whoever moves the request into the release step** (the app integration, next week) must first fill `Release_Contacts` and clear `Release_Flag`. A leftover "Reopened" would loop the request back.
4. **Reminders go to the first contact only.** The deadline reminders use `Assigned_Contacts.get(0)` (`Release_Contacts.get(0)` on the release step), the shape the builder made. If the builder lets you pick the whole field as the recipient, change it on one step, and I'll copy it to the others.
