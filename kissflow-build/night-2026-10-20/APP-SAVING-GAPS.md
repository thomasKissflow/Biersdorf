# App UI saving: how the portal does it, and what the app should change (20 Oct)

**Kissflow-internal.** Thomas asked that the app UI save the same efficient way as the portal UI. On 16 Oct the portal fix made saving fast and safe (kissflow-build/MORNING-2026-10-16.md §2, items 3 and 4).

This was a read-only comparison of prototype/src/app-live against prototype/src/portal. Every gap below was checked by a separate skeptical reviewer and **confirmed**. One gap was refuted: merging quick RMES saves is not needed, because "Save result" is an explicit click per criterion.

## The portal's saving rules (with evidence)

1. **Show the edit on screen at once and keep it there until it is saved**: Each setAnswer, saveConfig, setJustification or setComponents call goes into a per-case overlay ({answers, config, just, components}). The cases memo lays the overlay over the loaded case, and the scope is worked out again from the unsaved metadata answers. The user never waits for Kissflow to see an edit. _(prototype/src/portal/data/LiveSupplierStore.tsx:164-169 (Overlay), :180, :307-310 (enqueue writes overlay), :344-361 (cases = loaded case + overlay; liveScope recomputed :357), :391-417 (api setters all call enqueue))_
2. **Merge rapid edits: one queued patch per request, 700 ms debounce**: queue is a Map<caseId, AnswerPatch>. A new edit is mergePatch-ed into the request's queued patch (later wins per key; components replace as a whole). Each edit resets a 700 ms timer, so a burst of edits on one request becomes one save. isEmptyPatch skips edits that change nothing. _(prototype/src/portal/data/LiveSupplierStore.tsx:7-8 (header), :192-193, :303-315 (enqueue: isEmptyPatch :305, mergePatch :306, clearTimeout + setTimeout(flushNow, 700) :311-312); prototype/src/portal/data/answers.ts:66 (isEmptyPatch), :68-71 (mergePatch))_
3. **Commit text inputs on blur or Enter, not on every keystroke**: Text, number and longtext fields keep a local draft (useDraft) and call setAnswer only on blur or Enter. commit() returns early when the value equals the stored one. A justification saves on blur only if it changed. Range inputs use defaultValue + onBlur. Yes/no, select and multi-select commit at once and still go through the 700 ms queue. _(prototype/src/features/supplier/FieldRenderer.tsx:15-23 (useDraft), :55-59 (commit skips unchanged), :63, :83-92 (commitDraft), :193 and :212-213 (onBlur / Enter blurs), :198-200 (range defaultValue+onBlur), :152-174 (select/yes-no/multi commit directly), :301 and :314 (Justification onBlur only if draft !== value))_
4. **A draft never resets from reloaded or read-back data while the user types; it follows stored data only when the content really changed**: useDraft keeps a 'seen' copy of the stored string. It replaces the draft only when the stored value differs from what it last saw, not on every re-render or new object. ComponentTable (K2.1) does the same with a content key (incoming = JSON.stringify(c.components)) plus a dirty flag. A typing patch sets dirty, and while dirty an incoming content change only updates 'seen' and leaves the rows alone. commit() sets seen to the key of its own output, so its own save coming back does not reset the rows, and it skips setComponents when nothing changed. The whole row card commits on blur. Checkbox and Origin select commit at once (patch(..., true)). The old bug was comparing the array identity, which reset the rows after every reload. _(prototype/src/features/supplier/FieldRenderer.tsx:15-23; prototype/src/features/supplier/ComponentTable.tsx:39-50 (content key + dirty; comment :40-42 states the 16 Oct cause), :52-59 (commit: setDirty(false), setSeen(own key) :57, skip if key === incoming :58), :60-67 (patch: dirty while typing), :124-127 (row onBlur commits), :137 and :164 (immediate commit); regression scenario prototype/scripts/harness-portal.mjs:774-797 (k21-typing, 300 ms lag: CAS typed during the INCI save survives; both saved))_
5. **One serial write chain: autosave flushes, task actions and reloads never overlap**: serial(fn) chains every write onto chain.current, and the chain swallows rejections so one failure does not block later steps. flushNow, run (task actions), the reload after an action, reset and the header's Reload all go through serial. Two writes from the same tab can therefore never race each other, which matters because Kissflow drops one of two writes made within about 0.1 s. _(prototype/src/portal/data/LiveSupplierStore.tsx:231-237 (serial), :249 (flushNow on chain), :323 and :331 and :336 (run + reload on chain), :383 (reset), :532 (extras.reload), :553 (retry button))_
6. **Drain the queue when the save actually runs, so edits made during a save in flight are kept for the next one**: flushNow clears the timer, then takes queue.current only inside the serial step, when that step runs. An edit typed while an earlier save is in flight stays queued and on screen for the next flush. Once a save succeeds, its overlay keys are dropped only when no newer edit for the same key is waiting; components are dropped only when no newer components patch waits. _(prototype/src/portal/data/LiveSupplierStore.tsx:239-243 (doc comment), :244-251 (drain inside serial), :279-295 (overlay cleanup checks `waiting` per key :284-291))_
7. **Autosave = no full reload: show the request exactly as Kissflow read it back after the write**: patchRequest resolves with saveRequest's read-back item. When every queued request saved, flushNow calls withSavedRequests, which merges the read-back item into that bundle's request, keeps the original _activity_instance_id and leaves the task map alone, then rebuilds the supplier view. No task lists and no other items are read. The harness proves that autosaves make no extra PROCESS_GET_MY_TASKS_ITEMS calls: only the 5 lists of the first load. _(prototype/src/portal/data/LiveSupplierStore.tsx:9-10 (header), :116-125 (withSavedRequests), :260 and :264 (saved map), :275-277 (allSaved -> setData(withSavedRequests)); prototype/src/portal/data/liveActions.ts:158-168 (patchRequest returns saved.item); prototype/src/portal/data/answers.ts:170-171 (returns item: back); unit test prototype/src/portal/data/liveActions.test.ts:321-331 (tasks object unchanged, activity instance kept); harness prototype/scripts/harness-portal.mjs:798-799 (lists.length === 5))_
8. **Full reload only after task actions, uploads, file removal and a failed save**: run() (used by confirmCompleteness, supplierRespond, finalRelease, reportChange, uploadDocument, remove) runs serial(reload) on success and on failure. In flushNow, a failed save calls reload(), because the request may have moved on, for example to the release step. If that reload fails too, flushNow returns false and the on-screen copies stay. _(prototype/src/portal/data/LiveSupplierStore.tsx:317-342 (run: reload in .then :331 and .catch :336), :278 (failed save -> reload; return false keeps copies), :418-428, :440, :449, :519 (actions via run))_
9. **A task action first flushes pending edits on the same chain and is refused if they did not save**: run() calls flushNow() first, then queues the action behind it. Inside the step it awaits the flush result and throws ('Your latest answers were not saved, so this step was not sent') when that result is false. A step is therefore never submitted over answers that did not save. _(prototype/src/portal/data/LiveSupplierStore.tsx:317-328 (saved = flushNow(); if (!(await saved)) throw ...))_
10. **A failed save goes back into the queue (newer edits win); a locked request's edit is dropped**: When patchRequest throws an ordinary error, the case goes into keep (its overlay stays on screen) and the patch is re-queued as mergePatch(failedPatch, queuedNewer), so any newer edit wins. A LockedError (closed request, or the final release requested) is not re-queued, because it can never be saved, and the reload clears it. A 'Not saved: …' toast is shown in both cases. _(prototype/src/portal/data/LiveSupplierStore.tsx:256-258 (keep), :262-273 (catch: LockedError check :267, re-queue :270, notify :272), :283 (overlay kept for keep))_
11. **Save = 3 SDK calls: fresh read -> merge only own keys -> write only touched fields -> read back**: saveRequest reads the item fresh. Kissflow has no locking, so the patch is merged into what is stored now and never overwrites it blindly. applyPatch merges per key and stamps each key in Answered_By_JSON. docFields writes only the JSON fields the patch touched (plus Answered_By_JSON). Then it reads the item back. Derived data (Scope_JSON, Requested_Docs_JSON) and the presence fields (Editing_By, Editing_Since) ride in the same write, so they cost no extra call. _(prototype/src/portal/data/answers.ts:8-10 (rationale), :73-95 (applyPatch), :109-117 (docFields: touched fields only), :156-172 (saveRequest read :163, write :168, read back :169); prototype/src/portal/data/liveActions.ts:117-125 (io read = full item through the task, write = update), :142-146 and :163-165 (derived Scope/Requested_Docs in the same write))_
12. **Rev counter and change stamps on each save**: Every save writes Answers_Rev = stored + 1, plus Answers_Changed_At, Answers_Changed_By_Email, Editing_By and Editing_Since. The integration and service see one change signal, and the presence hint (a colleague saved here recently) comes from Editing_By/Editing_Since with no extra call. Uploads and removals bump the rev through bumpRev. _(prototype/src/portal/data/answers.ts:167-168; prototype/src/portal/data/liveActions.ts:170-185 (bumpRev); prototype/src/portal/data/map.ts:606-610 (presence from Editing_By/Since); prototype/src/portal/data/LiveSupplierStore.tsx:155-156 and :533 (presence))_
13. **Lost-write detection: compare the read-back with the patch and re-apply up to 3 times**: missingKeys lists every patched key whose stored value is not the same as the patch, using a JSON comparison. If any key is missing, saveRequest loops (fresh read, merge, write, read back) up to maxTries = 3, then throws a plain message with no field ids. writeVerified applies the same read, write, read-back-until-holds() loop (up to 3) to the other writes: upload files, completeness, the response, the release and the change report. _(prototype/src/portal/data/answers.ts:97-107 (missingKeys), :161-175 (loop + message); prototype/src/portal/data/liveActions.ts:148-156 (writeVerified), :201, :221, :299, :322, :343, :365, :384-405 (uses); tests prototype/src/portal/data/answers.test.ts:64 and :76, prototype/src/portal/data/liveActions.test.ts:138)_
14. **Refuse before writing on a locked request (checked on the fresh read)**: saveRequest throws LockedError on isWriteLocked(cur) before any write. patchRequest and uploadDocument also refuse at once when the request was loaded at the release or released step (requestOf, refuseAtRelease). The UI checks closed(id) before it queues anything. A refused change costs no write and is never retried. _(prototype/src/portal/data/answers.ts:140-142 and :164; prototype/src/portal/data/liveActions.ts:127-140, :161-162, :193-196; prototype/src/portal/data/LiveSupplierStore.tsx:369-377 (closed guard before enqueue); test prototype/src/portal/data/answers.test.ts:84 and :91, prototype/src/portal/data/liveActions.test.ts:280)_
15. **Hand-offs (webhooks) are fire-and-forget after the write and never block or slow the save**: handoff() runs `void client.postWebhook(...)` with an idempotency key, and only reports a failure through onSyncProblem (a warning toast). requestChanged fires after every successful patchRequest, upload and removal; a failed one heals with the next save. postWebhook uses fetch with no-cors and text/plain (no preflight), bounded to 30 s. The SDK api route is used only when fetch throws synchronously, never after a timeout, so a hand-off is not delivered twice. Submit hand-offs survive a lost submit answer by checking whether the item moved on (atStep). _(prototype/src/portal/data/liveActions.ts:69-81 (handoff, requestChanged), :82-97 (submitAndHandOff + atStep), :166, :222, :279; prototype/src/portal/data/client.ts:166-193 (postWebhook; comment :171 says the app UI does the same in src/app-live/kf/client.ts); prototype/src/portal/data/LiveSupplierStore.tsx:227 (onSyncProblem -> warning toast); tests prototype/src/portal/data/liveActions.test.ts:445, :483, prototype/src/portal/data/client.test.ts:232, :251)_
16. **SDK-first client as the signed-in user, every call bounded at 30 s (uploads 2 min)**: Every call goes through call() -> bounded(), which races the SDK promise against a 30 s timeout. ## The confirmed gaps in the app, most severe first

### 1. [high] Every save is followed by a full reload of everything, and the read-back is thrown away

- **App now:** When the last pending write settles, enqueue runs loadNow(true) (LiveAppStore.tsx:216). That calls loadSnapshot (:153; load.ts:420-483): every form list, the admin, task and my-items lists of every flow, and one full item read per listed review, open point and case. If a load effect then writes, a second full reload follows (LiveAppStore.tsx:172). The writers already hold the read-back (updateHeld returns `back` at actions.ts:103-113, formWrite resolves with it at :148-154, writeAudit reads its row back at audit.ts:82-86), but WriteResult has no field for it (types.ts:126-127), so it is dropped.
- **Portal:** An autosave shows the item exactly as Kissflow read it back after the write. patchRequest resolves with the read-back item (liveActions.ts:158-168), and flushNow merges it into the loaded data with withSavedRequests (LiveSupplierStore.tsx:116-125, :275-277). That merge keeps _activity_instance_id and the task map and reads nothing else. A full reload runs only after task actions, uploads and failed saves (:278, :317-342).
- **Impact:** A single 'Save result' on one RMES criterion costs about 6 write calls plus roughly 14 list calls and one item read per case, review and open point. 'Loading…' shows after every save. A click made during that reload waits behind it and then starts another full reload, so N saves a few seconds apart cost N full reloads. This is the slow-save pattern the portal removed.
- **Reviewer's check:** Confirmed. LiveAppStore.tsx:216 runs loadNow(true) once pending reaches 0. That calls loadSnapshot (load.ts:422-497): every granted form list, plus a formGet for each Supplier/RMES row (:447-455), the admin, task and My-items lists for case/review/op (for SAF that is about 15 lists), and a full read of each listed item. updateHeld (actions.ts:103-113), formWrite (:148-154) and writeAudit (audit.ts:79-88) all read the item back, but WriteResult (types.ts:126-127) has nowhere to carry it, so the read-back is dropped. recordCriterion costs 6 calls: formGet, formUpdate and formGet, then formCreate (create plus submit) and formGet. 'Loading…' is the header counter (:151), not a page block. A click made during the reload queues behind it, and pending reaching 0 again sets off another reload. So spaced saves each cost a full reload. This is the pattern the portal removed for autosave (LiveSupplierStore.tsx:275-278). Severity high stands.

**Do this:**

1. Add `saved?: { flow: FlowKey; item: RawItem }[]` and `auditRow?: RawItem` to WriteResult (app-live/types.ts:126).
2. Make updateHeld, formWrite and formCreated push their read-back into the job's Work (write/audit.ts), and make writeAudit return its read-back row.
3. In LiveAppStore.enqueue, when r.ok and the method moves no step and sends no hand-off that writes the item back (recordCriterion, addFinding, closeFinding, rmesDecision, reassignReview, addInternalNote, updateSupplier, addContact, updateContact, setContactActive):
   - replace those items in loadedRef.current.snap (items[flow] or forms[form], by _id, keeping the existing row's _activity_instance_id);
   - append the new note and audit rows;
   - rebuild with viewOf(snap, identity, acting) and setLoaded;
   - clear the optimistic state when the generation is unchanged;
   - skip loadNow.
4. Keep loadNow(true) only after step moves (createCase, raiseOpenPoint, findingToQuery, accept/not-accepted, closeOpenPoint, completeReview, reopenReview, cancelCase, sendDraft, discardDraft), after the op.round and op.edited hand-offs, and after any failed write.

### 2. [high] Queued actions still run after an earlier write failed, even a step submit

- **App now:** serial() swallows rejections (LiveAppStore.tsx:134-137), and a failed job only drops the optimistic state (:212-215). Jobs queued after it still run with the prev/next they built at click time on the failed action's optimistic state (api.ts:124-126, :145-152). completeReview writes Open_Count and RMES_Gaps from that state (write/actions.ts:433) and then submits (:445).
- **Portal:** run() flushes pending edits on the same chain and refuses the task action when they did not save ('Your latest answers were not saved, so this step was not sent', LiveSupplierStore.tsx:317-328, refusal at :324). A step is never submitted over data that did not reach Kissflow.
- **Impact:** A reviewer saves the last criterion result, or accepts the last answer, and at once clicks Complete review, which the optimistic state allows. The first write fails (VerifyError, a 429 after 3 retries, or the 30 s bound). completeReview still writes the counts as 0, Review_Gate reads OK, and it submits. The review is completed in Kissflow while a criterion or point is still open. The failure also hides the queued action's optimistic view.
- **Reviewer's check:** Confirmed. serial (LiveAppStore.tsx:134-137) keeps the chain going, and a failed job only toasts and calls setOptimistic(null) (:212-215). Jobs queued later still run with the prev/next they captured at click time (api.ts:124-126, :146-148). completeReview writes countsOf(c0) (actions.ts:433), and c0 comes from that click-time prev, which includes the failed action's optimistic result. Review_Gate is the formula IF(Open_Count+RMES_Gaps=0,"OK","") (plan-v5 §481), so it trusts these client counts. The staleCheck on the review item does not see a failed RMES-form or open-point write. The scenario holds: a recordCriterion or reviewResponse accept fails, the Complete review clicked straight after it still submits, and the review closes with a criterion or point still open. setOptimistic(null) also wipes later queued actions' optimistic views. The portal refuses a task action when its pending saves failed (LiveSupplierStore.tsx:324).

**Do this:**

In LiveAppStore.enqueue (app-live/LiveAppStore.tsx:195-220):
1. Add `const failEpoch = useRef(0)`.
2. Capture `const epoch = failEpoch.current` when the job is enqueued.
3. Inside the serial step, when `failEpoch.current !== epoch`, do not run the job. Settle it as `{ ok: false, tone: 'warning', message: 'Not sent: an earlier change on this page was not saved, so this one was not sent either. Check the screen and try again.', handoffs: [], warnings: [] }`.
4. Increment failEpoch.current whenever a job's result is not ok, before setOptimistic(null).

This mirrors the portal's run() refusal at LiveSupplierStore.tsx:324.

### 3. [high] A submit whose answer is lost skips the hand-offs and the audit row, although the step moved

- **App now:** createStarted turns any submit error into a 'saved as a draft but not sent' Stop (write/actions.ts:139-143). submitGated (:116-120) and completeReview (:445) rethrow. The hand-offs and recordAudit that follow are skipped: :196-199 (op.round, history), :272-276, :330-334, :536-545 (case.started, case.created). No check is made whether Kissflow actually moved the item.
- **Portal:** submitAndHandOff catches a failed submit and asks moved() (atStep: is the item at the next step among my tasks?). A proven move counts as success, so the hand-off is still posted (liveActions.ts:82-97).
- **Impact:** Sometimes the 30 s bound fires after Kissflow has already moved the item. In that case:
- A new case never sends case.started, so I-1 never creates the portal request and the supplier is never invited. It also gets no case.created row, which is the case index other roles read.
- A raised point never sends op.round, so the supplier never sees the question.
- The user reads 'draft, open Diagnostics', but Diagnostics lists nothing, because the item is no longer a draft.
- **Reviewer's check:** Confirmed. createStarted turns any submit error into the 'saved as a draft… open Diagnostics' Stop (actions.ts:139-143). submitGated (:119) and completeReview (:445) rethrow, so the hand-offs and recordAudit after them never run: raise :198-199, reviewResponse :275-276, closeOpenPoint :333-334, createCase :539-545. Nothing checks whether the item actually moved. Diagnostics lists only items whose _status is still Draft (load.ts:519-527), and nothing else re-sends case.started (no other sender in activation.ts or load.ts). A moved case would therefore never reach I-1, and RMM might create it again. The trigger is rare (the submit lands but its answer is lost, e.g. after the 30 s bound at kf/client.ts:116-122). The portal handles exactly this case (liveActions.ts:82-97). The consequence is severe but rare, so medium-high rather than high.

**Do this:**

In app-live/write/actions.ts:
1. Add `submitOrMoved(ctx, flow, id, act)`. It calls ctx.client.submit; on an error it re-reads once with ctx.client.getTask(flow, id, act).
2. Treat any of these as proof that the step moved:
   - a refusal matching verify.ts QUEUE (050201, 'moved out of your queue');
   - an item whose _status is no longer 'Draft' (createStarted);
   - an item whose current activity instance is no longer `act` (held steps).
3. Rethrow the original error only when no move is proven.
4. Use it in createStarted (:140), submitGated (:119) and completeReview (:445), so the hand-offs and the audit row still go out.
5. Check the probe once live. It is [unverified]: which answer getTask gives for an item that has moved.

### 4. [medium] The stale check compares with the newest reload, not with the data the user clicked on

- **App now:** api.ts write() builds prev/next and a ctx at click time (:124-132), but runs the writer with `deps.ctx()` (:148), which reads loadedRef.current at job time (LiveAppStore.tsx:231). heldOp and staleCheck therefore compare Kissflow's _modified_at with the latest load (actions.ts:103-113, verify.ts:139-153). Thread_JSON and the other fields come from the click-time op (actions.ts:258-270, :300, :326).
- **Portal:** saveRequest reads the item fresh and merges only its own keys into what is stored now, so it never writes from an old copy (answers.ts:156-172).
- **Impact:** The user saves action A and its full reload starts. During that reload they click B, which is built from pre-reload data.
